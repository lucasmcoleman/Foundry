# Foundry audit and review — 2026-09-10

## Assessment and scope

Foundry has a useful hardware-aware pipeline and substantial regression coverage,
but several boundaries were checked by configuration flags or file existence
rather than observed behavior. This review found actual supervision, export,
resume, packaging, and publication defects despite a passing baseline suite.
The highest-value next feature is a durable run/artifact manifest joining all
stages, evaluation, and publication.

Scope: tracked `core/`, `ui/`, `foundry_gym/`, tests, packaging, CI, deployment
configuration, and integration with sibling MagicQuant. Evidence includes local
code inspection, actual TRL/PEFT behavior on tiny CPU fixtures, HTTP test doubles,
subprocess tests, upstream-generated GGUFs, and installed-wheel checks. No live
training, model uploads, server changes, credential reads, or production data
modifications were performed. This is not an exhaustive security or hardware
performance certification.

## What is good

1. Streaming loading/export reflects the actual unified-memory hardware rather
   than assuming a conventional dedicated-VRAM setup.
2. Shared service builders and importable stage entries reduce CLI/UI drift.
   Many configuration and decision helpers are testable without a GPU.
3. Smoke-test quarantine prevents a known pathological GGUF from being picked
   up by a later upload glob. Source-resolution errors and fork-format warnings
   often fail visibly rather than inventing a fallback result.
4. Publishing criteria distinguish size bands, quality noise, speed tradeoffs,
   and budget builds. Model cards attempt to explain missing and carried-over
   files; those are worthwhile product requirements.
5. The baseline offline suite passed 840 tests with one skip. Existing PEFT
   differential tests, workflow equivalence tests, and the Gym's 177 verifier
   tests provide a good foundation. The gap was what those tests observed.

## Implemented findings

### P1 — Completion-only training did not actually mask prompts

`core/_train_entry.py` and the standalone trainer converted conversations to
plain text and passed `completion_only_loss=True`. The installed TRL collator
only applies that mask when the example carries `completion_mask`; the original
text path did not produce one. System/user tokens therefore remained labels.

`core/dataset_format.py:tokenize_training_example` now creates explicit token
masks for every assistant turn. Tests use the real TRL collator and a tiny local
SFTTrainer to inspect the actual batch labels. Raw text retains ordinary language
model loss. An example truncated before all targets fails clearly.

**Compatibility:** templates that change earlier turns while rendering prefixes,
or tokenizers without character offsets, are rejected rather than guessed.
Packing retains the explicitly requested full-text-loss behavior. This change
needs a controlled training experiment before making model-quality claims.

### P1 — Changed data/configuration could resume an unrelated checkpoint

The old trainer chose the highest checkpoint directory regardless of current
inputs. Correcting the loss mask or stage hash alone could therefore resume the
old optimizer state and even complete without new steps.

`core/training_state.py` records a supervision-schema/configuration/local-input
identity before model loading and selects only complete matching checkpoints.
Unknown or changed provenance fails before GPU work and preserves existing files.
Use a new output directory for legacy or incompatible checkpoints.

### P1 — Completion markers accepted stale or incomplete artifacts

Markers previously accepted a nonempty recorded **or** requested artifact and
ignored recorded size. Export hashes identified an adapter directory by path;
training it again in place could reuse the earlier merge. A successful process
exit or metadata file did not prove that all model shards or QAT weights existed.

`core/markers.py` now checks the exact requested artifact, size/mtime, essential
metadata and sibling-shard inventory, safetensors index references, and QAT
adapter presence. Stage hashes include selected local inputs, and prior markers
are invalidated before outputs are rewritten. Tests cover same-size replacement,
missing shards, wrong-file substitution, malformed markers, and exit-zero/no-output.

**Limit:** fingerprints use size and nanosecond mtime to avoid rereading enormous
models. They detect ordinary edits, not malicious tampering or remote revision
changes. Old marker hashes may cause a one-time rerun.

### P1 — Streaming export could silently omit trained changes

`core/fast_export.py` now validates complete adapter pairs and target coverage,
supports per-module rank/alpha scaling, rejects non-finite merges, and fails
clearly for unsupported PEFT adapter features. It preserves tokenizer assets,
accepts local safetensors sources without a Hub download, permits valid Hub cache
symlinks, and protects a source GGUF already at the destination path.
Real PEFT save/merge and safetensors tests verify the results on CPU.

**Compatibility:** unsupported DoRA, transposed layouts, trainable biases,
saved modules, token embeddings, and other adapter variants require a supported
PEFT merge path; they no longer silently export an incomplete model.

### P1 — Upload failures could still report success

`core/hf_upload.py` previously swallowed model-card validation/publication
failures and published the card before all model files existed. It now stops on
contradictory cards or unavailable repository listings, uploads files before the
card, checks the resulting file list, and reports failure if publication is
incomplete. A requested dataset upload failure is also a failure. Dry-run access
checks treat only HTTP 404 as an absent repository.

Retries now handle both requests and HTTPX transport errors, throttling, and
server failures; permanent authentication/validation errors are not retried.
This matters because [Hub 1.x changed HTTP clients](https://huggingface.co/docs/huggingface_hub/en/concepts/migration).
Tests stub every Hub operation; nothing was uploaded.

Training-dataset publication is now **opt-in** (`--upload-dataset` or the UI
checkbox). Naming a dataset for the card or publishing a model does not imply
permission to publish private training examples. Explicit saved choices remain.

**Limit:** file uploads are still individual commits. A failure can leave a
partial remote repository; this patch reports that honestly but is not a
transactional release system.

### P2 — Installed artifacts and integration metadata were incomplete

The wheel omitted `ui/index.html`, and `foundry-upload` failed to import its
package without the checkout's `core/` path injection. Explicit package data,
package-import fallbacks, declared HTTP dependencies, and `tools/check_wheel.py`
close those gaps. The smoke check imports console entry points and serves the UI
outside the source tree. Budget output renaming now updates `v2_results.json`
and its anchor references, with rollback if metadata publication fails.

CI now includes built-wheel checks, Python 3.10/3.12, required Pyflakes checks,
the Gym suite, and a CPU training/export lane. `make` prefers the local virtualenv
and supports `PYTHON=...`. The original package failures were reproduced before
checking corrected wheels.

### P1 — Browser inputs and job cancellation needed stronger boundaries

`ui/index.html` inserted saved values and history filenames into HTML attributes
and inline handlers. Rendering now escapes attribute/text values and binds
history actions as event listeners. Tests execute the actual rendering functions
in Node and inspect the resulting HTML for injected elements and handlers.
REST and WebSocket handlers reject foreign browser origins; token comparison
also handles non-ASCII input without raising an internal error.

Stop requests retain the active-job reservation until teardown finishes, including
requests made before the background runner starts. Cancellation reaps processes;
descendant tracking reaches measurement workers that open their own sessions
and retains their identities through the TERM/KILL grace period. Real tiny
process tests cover a detached worker and a worker that ignores TERM. This is
best-effort cleanup; a cgroup is needed for stronger containment during races.
WebSocket sends have timeouts and tolerate concurrent disconnects, preventing
a stalled or closing browser from blocking stdout indefinitely or failing a job.
Nanosecond stage-log names avoid overwriting fast consecutive stages. Completion
events distinguish success, failure, and user stop. This remains one UI process's
coordination, not a durable cross-process job scheduler.

Compose now publishes on loopback and requires a key by default. Settings move
to a writable, atomic `~/.foundry/config.json` (or `FOUNDRY_CONFIG_PATH`), with
legacy checkout fallback and a persistent Compose volume. The sibling MagicQuant
Dockerfile path is corrected. See README migration notes for keys and browser
origins; container execution itself was not validated in this audit.
Installed UI code and runtime data also have separate roots: an installed
package uses the working directory or `FOUNDRY_WORK_DIR` for jobs, while stage
imports retain the package's code path. The wheel check executes a tiny worker
and verifies its log is outside `site-packages`. Relative local data/output paths
are resolved before launching stage entries.

### P2 — Gym execution guarantees were overstated

The runner nonce is visible through candidate-accessible Python frames; a benign
test confirmed this. It is a protocol marker, not authentication. Expected
outputs remaining in the parent is still useful, but the child retains its user
account's filesystem permissions and can bypass Python socket stubs.

The code/docs now state that limitation. Patches handle short pipe writes,
malformed protocol values, and reward-batch length mismatches. A real container/VM
boundary remains necessary for unknown candidate code. Never treat this runner
as permission to expose host credentials, mounts, or network access.

## Product, evaluation, and operational recommendations

1. **A reviewable release plan before publishing.** Present source revision,
   transforms, actual files, measured/predicted/unknown status, rejects, carried
   artifacts, destination, and dataset-publication choice. Use a staged or
   transactional commit for each repository. The
   [Hub upload documentation](https://huggingface.co/docs/huggingface_hub/en/guides/upload)
   describes multi-file commit options; integration still needs explicit policy
   for large uploads, retries, and concurrent repository updates.
2. **Durable jobs and observable failures.** Persist job/stage IDs, progress,
   heartbeat, exit reason, selected inputs, subprocess group, and cancellation
   status. Recover after UI restart and distinguish resumable failure from a
   completed stage. Bound logs and apply backpressure to slow WebSocket clients.
3. **Resource planning and retention.** Check/reserve disk as well as memory;
   account for source, merged model, BF16 conversion, temporary quants, optimizer
   checkpoints, and upload staging concurrently. Offer explicit retention plans
   and integrity checks before deleting anything.
4. **Evaluation for actual use.** Perplexity alone does not establish coding,
   tool use, JSON validity, long-context, or multilingual quality. Keep independent
   calibration/search/evaluation splits; use control arms for QAT and repeated
   latency/throughput measurements with uncertainty and fixed conditions.
5. **A supported dependency matrix.** The existing Foundry environment's
   `pip check` reports missing `lm-eval` and incompatible numpy/PEFT requirements
   for the installed optional stage tool. It was not modified. Isolate conflicting
   stage environments and record their versions rather than repeatedly upgrading
   one shared ROCm environment. Validate the pair of MagicQuant/Foundry revisions
   actually shipped together, not just each repository's latest default branch.
6. **A clearer user contract.** Show a resolved stage plan and source path before
   execution, surface destructive/requantizing operations and skipped quality
   checks, and explain why an option is unavailable. Consolidate historical docs;
   make current architecture, supported workflows, and migration notes discoverable.

## Things easy to overlook

- Is a successful model upload allowed to expose the training corpus too?
- Can a later run distinguish a fresh QAT/REAP output from an older artifact
  with the same directory name?
- Does a high reward indicate solving unseen tasks, or learning verifier-specific
  shortcuts? Keep private evaluation seeds and separate capabilities from format
  compliance.
- Can a browser tab, second worker, CLI job, or resumed checkpoint invalidate
  the assumptions of an already-running job?
- Can a model card prove which source, adapter, corpus, backend, and measurements
  belong to a file once local intermediates are gone?
